================================================================================
LEXIPATH API - ROUTE REFERENCE
Scope: Implemented prototype routes, including student recommendations.
Base path: /api
================================================================================

CONVENTIONS
-----------
- All request and response bodies are JSON, except sample upload (multipart)
  and image serving (binary).
- IDs are generated by the server. Clients never send an id when creating.
- Error responses use a single shape:
      { "error": { "code": "SAMPLE_NOT_FOUND", "message": "..." } }
- Status codes used: 200 OK, 201 Created, 202 Accepted, 400 Bad Request,
  404 Not Found, 422 Unprocessable Entity, 500 Internal Server Error.
- No authentication in the prototype. This is a deliberate cut, not an
  oversight - see NOTES AND DEFERRED at the bottom.


================================================================================
STUDENTS
================================================================================

POST /api/students
------------------
Creates a new student record.

Body:     { "name": String, "currentGrade": String, "teacherId": String? }
Returns:  201 + the created Student, including the server-generated studentId.
Errors:   400 if name or currentGrade is missing.

Notes:
  - studentId is minted by Mongo. Do not accept one from the client.
  - teacherId is optional while there is no auth. Once login exists it comes
    from the session instead of the body.


GET /api/students
-----------------
Lists all students.

Returns:  200 + array of Student objects.

Notes:
  - With no auth this returns every student in the database. Acceptable for
    the prototype; would be scoped to the logged-in Teacher in production
    (Teacher "may teach" Student, 0..*).


GET /api/students/:studentId
----------------------------
Fetches one student's core details.

Returns:  200 + Student { studentId, name, currentGrade }
Errors:   404 if no student with that id.

Notes:
  - Does not embed samples or reports. Use the routes below for those - keeps
    the payload predictable and avoids an expensive join on every profile load.


GET /api/students/:studentId/samples
------------------------------------
Lists the samples belonging to one student. Backs the UI's select(sample).

Query:    ?status=PENDING|PROCESSING|COMPLETE|FAILED   (optional filter)
Returns:  200 + array of Sample summaries:
              { sampleId, uploadedAt, analysisStatus, imageCount }
Errors:   404 if the student does not exist.

Notes:
  - Deliberately a summary, not the full Sample. Do not return sampleImages or
    sampleContent here; the list screen does not need them and the payload
    grows fast.
  - Sort newest first. The therapist almost always wants the latest upload.


================================================================================
SAMPLES
================================================================================

POST /api/samples
-----------------
Uploads a new handwriting sample and starts analysis.

Content-Type: multipart/form-data
Fields:   studentId  (String)
          images     (one or more image files)
Returns:  202 + the created Sample, with analysisStatus = PROCESSING and the
          server-generated sampleId.
Errors:   400 if studentId is missing or no file was attached.
          422 if validateSample() rejects the file (wrong MIME type,
          oversized, unreadable).

Maps to:  SampleController.validateSample(sample) -> submitSample(studentId, sample)

Notes:
  - The client does NOT send a sampleId. It reads it off the response and uses
    it to poll.
  - 202, not 201: the Gemini vision call takes seconds, so the request returns
    as soon as the Sample row exists and analysis continues in the background.
    ErrorClassificationEngine.analyse() runs after the response is sent.
  - DECISION POINT: if you would rather block until the report exists, this
    becomes 201 + SampleReport and GET /samples/:sampleId stops being needed
    for polling. Blocking is simpler to write but ties up a connection for the
    full model latency and gives the UI no progress state. Pick one and make
    sure the UC1 sequence diagram draws the return arrow in the matching place.


GET /api/samples/:sampleId
--------------------------
Fetches one sample's metadata. This is the polling target after upload.

Returns:  200 + Sample { sampleId, studentId, uploadedAt, analysisStatus,
                         imageCount, sampleContent? }
Errors:   404 if no sample with that id.

Notes:
  - The client polls this until analysisStatus is COMPLETE, then requests the
    report. Suggested interval: 2s, with a ceiling so a failed job does not
    poll forever.
  - If analysisStatus is FAILED, include the reason so the UI can show
    something better than a spinner that never stops.


GET /api/samples/:sampleId/images/:index
----------------------------------------
Serves the raw scan image bytes for the review screen.

Params:   index - zero-based position in the sample's image array
Returns:  200 + image bytes, with the correct Content-Type
Errors:   404 if the sample or that index does not exist.

Notes:
  - Indexed because Sample.sampleImages is Image[*] - a sample can be several
    pages. imageCount from the Sample payload tells the client how many exist.
  - Files live on disk (not GridFS at prototype scale), so this route resolves
    the stored path and streams it. Never expose the filesystem path itself in
    any JSON response.


GET /api/samples/:sampleId/report
---------------------------------
Fetches the error report for one sample. This is the main payload behind the
scan-beside-errors review screen.

Returns:  200 + SampleReport {
              reportId, sampleId, generatedAt,
              statistics: { ... },
              detectedErrors: [ { errorId, originalText, locationOnScan,
                                  confidenceScore, category, status,
                                  previousCategory, correctionNote,
                                  correctedAt } ]
          }
Errors:   404 if the sample does not exist, or if analysis has not finished
          yet - the client should be polling GET /samples/:sampleId instead.

Maps to:  ReportController.getErrorReport(sampleId) : SampleReport

Notes:
  - detectedErrors is embedded, not linked. DetectedError is composed into
    SampleReport, so it has no independent existence and gets no standalone
    read route. One request loads the entire review screen.
  - locationOnScan is what lets the UI draw the highlight over the image, so it
    must survive serialisation intact.


================================================================================
ERROR CORRECTION
================================================================================

PATCH /reports/:reportId/errors/:errorId
--------------------------------------------
Applies a therapist's correction to a single detected error.

Body:     { "action": "CONFIRM" | "RECATEGORISE" | "REMOVE",
            "newCategory": String?,      // required when action=RECATEGORISE
            "correctionNote": String? }
Returns:  200 + the updated SampleReport (statistics included, already
          recalculated).
Errors:   400 if action is unrecognised, or RECATEGORISE arrives without a
          newCategory.
          404 if the report or error id does not resolve.

Maps to:  ReportController.modifyErrorTag(errorId, action, newCategory, note)

Notes:
  - PATCH, not PUT. This is a partial update of a few fields; PUT means
    "replace the whole resource with the body I am sending", which is not what
    happens here.
  - REMOVE is also PATCH, not DELETE. The record is kept and status flips to
    REMOVED, because the correction history is the audit trail. Deleting the
    row would destroy the evidence that the AI got it wrong.
  - The handler sets previousCategory (from the old category), correctionNote,
    and correctedAt before saving.
  - Returns the whole report rather than the single error because
    recalculateStatistics() has run and the summary panel needs the new numbers.
  - HOT SEAM: this is where RecommendationReport.markOutdated() will be called
    once the recommendation leg exists. Leave the hook, even if it is a no-op
    for now - retrofitting it later means touching this handler again.


================================================================================
TRENDS
================================================================================

GET /api/students/:studentId/trends
-----------------------------------
Returns aggregated error trends across all of a student's samples.

Query:    ?from=YYYY-MM-DD&to=YYYY-MM-DD   (optional; defaults to all time)
Returns:  200 + TrendData - counts and proportions per error category over the
          range, plus a per-sample series for the chart.
Errors:   404 if the student does not exist.
          400 if from or to is unparseable, or from is later than to.

Maps to:  ReportController.getErrorTrends(studentId, range)
          -> aggregateByCategory(sampleReports)

Notes:
  - Computed on demand from the stored SampleReports. There is no persisted
    trend entity, by design.
  - MUST exclude errors with status = REMOVED. A therapist who deleted a false
    positive expects it gone from the trend line. Getting this wrong makes the
    dashboard quietly disagree with the review screen.
  - Only samples with analysisStatus = COMPLETE contribute.

================================================================================
RECOMMENDATIONS
================================================================================

POST /api/students/:studentId/recommendations
------------------------------------------------
Generates one latest-only student recommendation report.

Body:     {}
Returns:  201 + { "report": RecommendationReport }
Errors:   400 malformed student ID; 404 missing student; 422 no active
          analysed/reviewed errors; 500 missing live configuration;
          502 upstream Azure or Gemini failure.

Notes:
  - Uses all ANALYSED and REVIEWED samples, oldest first.
  - Excludes errors with dismissed = true and preserves written exactly.
  - Generation finishes before the atomic upsert, so failure retains the
    previous report.
  - Returns at most four strategies and three approved worksheets.
  - There is no sample-level recommendation route or report history.


GET /api/students/:studentId/recommendations/latest
----------------------------------------------------
Returns the student's current report without regenerating it.

Returns:  200 + { "report": RecommendationReport, including isOutdated }
Errors:   400 malformed student ID; 404 no report generated.

Notes:
  - isOutdated is true when a contributing sample changed after generation,
    or when a new ANALYSED/REVIEWED sample is missing from basedOnSamples.


GET /api/worksheets/:worksheetId/file
--------------------------------------
Opens an approved private Azure worksheet through the server.

Returns:  200 + PDF bytes with inline, nosniff, and private-cache headers.
Errors:   404 arbitrary or unapproved ID; 502 invalid, oversized, or
          interrupted upstream PDF.

Notes:
  - The client sends only the stable worksheet ID.
  - The server resolves the private Blob path and never exposes the SAS token,
    signed URL, or path in JSON.


GET /api/recommendation
-----------------------
Returns the original compatibility response. It is not used for generating
student reports and remains unchanged while older callers migrate.

================================================================================
NOTES AND DEFERRED
================================================================================

VERTICAL SLICE COVERED BY THE ABOVE
  create student -> upload sample -> poll status -> view report -> correct an
  error -> view trends. That is a complete demoable path with no gaps.

DEFERRED - AUTH
  No login route exists. Teacher is in the domain model but nothing enforces
  ownership, so every route is effectively public and GET /api/students returns
  everyone. Fine for a prototype demo; record it as a known cut so it does not
  get discovered live during the presentation.

ROUTE COLLISIONS TO AVOID
  Two routes that differ only by parameter NAME are the same route. Express
  matches on position, so /reports/:sampleId and /reports/:studentId collide
  and whichever registers first wins silently. Every collection above is nested
  under the resource that owns it, which is what keeps them distinct.
